# Обновления WinUp: что сделано и как пользоваться

Дата: 6 октября 2026 года. Версия приложения: 1.13.0.

Репозиторий: https://github.com/BodySan/winup. В нём находятся код, лицензии, сборочные инструменты и проверки. Личные базы, пароли, PIN, ключи Windows Hello и закрытый ключ выпусков туда не загружались.

## Какой способ выбрать

| Способ | Твои действия | Действия брата | Ограничения |
|---|---|---|---|
| Подписанный комплект с GitHub | Запустить `Выпустить обновление.cmd`, дождаться проверки и публикации; затем обновиться в WinUp | В WinUp нажать проверку, скачать комплект, перезапустить | Нужен интернет. Новая функция или несовместимое изменение требуют новой сборки приложения |
| Тот же комплект из файла | Передать `components.wup`; выбрать его через «Установить из файла» | Получить файл, выбрать его в том же окне, перезапустить | Интернет для установки не нужен. Подпись проверяется самим WinUp |
| Новое приложение целиком | Закрыть WinUp, проверить подпись нового EXE и заменить его | То же | Самый простой способ для редких крупных изменений. Папку `data` сохранять |
| KeePass / WinFsp отдельно | Кнопки этих компонентов в окне обновлений | То же | Программа проверяет официальный выпуск. Установка драйвера требует прав администратора; возможна перезагрузка Windows |

Для повседневного использования рекомендую комплект с GitHub и локальную подпись. Для двух компьютеров, которые обновляются редко, передать тот же `.wup` вручную почти так же удобно. Интернет-источник можно отключить пустым адресом в настройке источника.

| Где подписывать | Сколько действий | Главный компромисс |
|---|---|---|
| На твоём ПК по команде — настроено | Один запуск команды для выпуска; затем кнопки установки на обоих ПК | Ключ остаётся у тебя. GitHub сам не публикует доверенный комплект |
| На твоём ПК по расписанию — не настроено | После отдельной настройки можно выпускать без ручного запуска | ПК должен быть включён и иметь доступ к GitHub; защита локального ключа остаётся критичной |
| В GitHub Actions — не настроено | Можно выпускать, даже когда твой ПК выключен | GitHub должен получить секрет подписи. Захват процесса подписи позволяет изготовить доверенное поддельное обновление |

GitHub шифрует сохранённые Secrets, но разрешённый процесс подписи должен получить секрет для использования. Злоумышленник, управляющий этим процессом, может украсть его или сразу подписать вредоносный пакет. Поэтому «секрет зашифрован в GitHub» не означает «взломанный workflow не сможет им воспользоваться». Полностью автоматическую облачную подпись сейчас не включал.

В программе: меню → «Обновления компонентов…» → «Проверить» → «Скачать комплект» → «Перезапустить». Вариант из файла находится в этом же окне. Отдельно доступны KeePass, WinFsp и откат. Изменения начинают действовать при следующем запуске.

## Что делает автоматика

Раз в неделю GitHub Actions ищет новые стабильные совместимые версии Bouncy Castle, CBOR, Numbers и списка доменных суффиксов. Готовит кандидат, пересобирает адаптер и запускает проверки на одноразовой Windows-машине. Не получает доступ к твоему компьютеру и хранилищам.

После успешных тестов кандидат ещё не становится доверенным обновлением. Команда на твоём ПК запускает свежую проверку, скачивает кандидат, сверяет собственные исходники с локальной доверенной копией, отдельно получает подписанные официальные NuGet-пакеты и сверяет DLL. Затем воспроизводимо пересобирает адаптер, локально пересобирает EXE, подписывает комплект и публикует выпуск. Брату эти операции повторять не нужно.

PSL сверяется с официальными байтами либо с уже доверенной встроенной копией. Если узел сети выдаёт устаревший список, новая программа сохраняет более свежую встроенную копию; кэш не может понизить её версию.

Зелёная отметка GitHub сама по себе не является защитой: её недостаточно для подписи. Если кто-то изменит твой код только в GitHub, локальный выпуск будет остановлен.

Cryptomator и Java остаются согласованным комплектом оригинального файлового ядра. Проверка показывает новые CryptoFS/Cryptolib, но не заменяет отдельные JAR автоматически. Их новая версия может потребовать изменений адаптера и отдельной приёмки. Основная новая версия прочих библиотек тоже не принимается автоматически. Автоматика выявляет проверяемые сбои; код за разработчика не исправляет.

Сетевое описание выпуска действует 28 дней. Если долго не выпускать новый комплект, программа откажется устанавливать старое сетевое описание. Новый запуск команды выпуска создаст свежий подписанный комплект. Локальный файл `.wup` проверяется по подписи и совместимости независимо от сетевого срока. Откат сохраняет номер последнего принятого выпуска: тот же номер повторно не ставится, нужен следующий выпуск.

## Риски на простом языке

**Подпись — это личная печать владельца приложения.** В WinUp встроена возможность проверить её, но изготовить поддельную печать по этим данным нельзя. GitHub хранит файл и результат подписи; секрет для её создания хранится отдельно на твоём ПК.

**Если взломают только GitHub:** злоумышленник сможет удалить выпуск, мешать загрузке, изменить открытый код или положить фальшивый файл. Поддельный комплект установленный WinUp отвергнет. Локальная команда также откажется подписывать изменённые собственные исходники. Это защищает канал обновлений, но не гарантирует доступность сервиса.

**Если скачивать и запускать EXE вручную:** установленная программа уже не контролирует замену самого себя. Поэтому для нового EXE нужна проверка `.sig` старым доверенным проверяющим скриптом и старым публичным ключом. Проверяющий скрипт и новый ключ, скачанные вместе с подделкой, защиты не дают. `Проверить подпись.cmd` проверяет EXE рядом с собой; на него можно перетащить другой EXE, рядом с которым лежит соответствующий `.sig`. Первая передача программы брату должна идти по доверенному каналу, чтобы у него появилась доверенная исходная копия.

**Если взломают твой Windows-профиль:** вредоносная программа может расшифровать локальный ключ подписи через DPAPI от твоего имени, изменить сборщик и подписать подделку. В незаблокированном хранилище она также может украсть открытые пароли. GitHub здесь не нужен. DPAPI помогает против копирования файла ключа вне профиля, но не против вируса, работающего под твоей учётной записью.

**Если новая официальная библиотека содержит ошибку или вредоносный код:** официальная подпись подтвердит происхождение, а не отсутствие всех проблем. Наши проверки ловят известные сценарии, но не являются доказательством абсолютной безопасности. Поэтому есть ограничения версий и откат, а неподдерживаемые обновления не устанавливаются автоматически.

**Если потерять локальный ключ:** уже выпущенные файлы продолжат проверяться. Новые пакеты этим ключом подписать не получится. Файл `.release-private/component-signing.dpapi` привязан к Windows-профилю; сохранить только его на флешку недостаточно для гарантированного восстановления после переустановки Windows. Нужна проверенная резервная копия профиля/системы. При утрате понадобится новая сборка с новым публичным ключом.

## Как снизить риск GitHub

1. Оставить ключ выпусков локальным — так настроено сейчас. В GitHub Actions секрет с ним не создавался. Публичность кода не даёт права записи посторонним и не открывает личные хранилища.
2. Для входа в GitHub использовать ключ доступа или аппаратный ключ и сохранить резервный способ входа с кодами восстановления. Это нужно включить владельцу аккаунта. [Документация GitHub](https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/configuring-two-factor-authentication).
3. Не выдавать лишним людям и приложениям права записи. Рабочие задания используют токен только для чтения, не сохраняют учётные данные checkout, внешние действия закреплены за конкретными commit SHA. [Рекомендации GitHub](https://docs.github.com/en/actions/reference/security/secure-use).
4. Пользоваться встроенной установкой подписанного комплекта. При ручной замене EXE проверять его подпись доверенной локальной копией проверяющего инструмента.
5. Хранить резервные копии зашифрованных баз и проверенный способ восстановления ключа. Подпись обновлений не заменяет резервное копирование данных.

Полностью исключить риск нельзя. Наиболее сильное дальнейшее усиление — отдельный офлайн-компьютер для подписи или аппаратный ключ, пригодный для подписи выпусков. Это потребует отдельной реализации и добавит действия при выпуске. Для двух пользователей текущий вариант с локальной подписью практичнее.

## Что проверено

- В Windows Sandbox с искусственными данными: 126 проверок функциональности и защиты, включая подмену и повреждение пакета, чужую подпись, лишние файлы, выход из ZIP-пути, несовместимую версию, повтор старого выпуска, откат, повреждённое состояние и сбои загрузки.
- Настоящий подписанный комплект с Bouncy Castle 2.7.0: установка из файла, следующий запуск, операции ключей доступа, шифрование/расшифрование файла, откат и возврат к встроенным компонентам после повреждения.
- Настоящая загрузка по HTTPS: плохая подпись и изменённые байты отвергнуты; корректный комплект установлен и использован новым процессом.
- Настоящие Edge и Chrome в песочнице: регистрация ключа доступа, вход с проверкой цифровой подписи, запрет чужого домена, показ 2FA, скрытие кода после блокировки.
- Трей: галочка сохраняет настройку и не сворачивает окно; кнопка сворачивания скрывает его в трей; одиночный/двойной щелчок и меню возвращают окно; отключённая настройка возвращает обычное сворачивание.
- GitHub Actions: полный прогон Windows и 24 проверки браузерного JavaScript. Это проверка определённых сценариев, а не полный ручной анализ всех библиотек.
- Реальный публичный выпуск GitHub №100003: проверены сетевое описание, подпись, скачивание, установка и операции ключей доступа/файлового ядра в новом процессе песочницы.
- Переход с №100003 на №100005 в том же синтетическом профиле: загрузка, установка и работа обоих криптомодулей после запуска отдельного процесса — успешно.
- Полный выпуск №100005 одной локальной командой: свежие тесты №37495258494, независимая проверка кандидата, локальная сборка/подпись, публикация — успешно.
- Подпись EXE: правильный файл принят; изменённый EXE и пара «поддельный EXE + подпись чужим ключом» отвергнуты доверенным локальным проверяющим инструментом.
- Имитация подмены исходника в кандидате: изменённый `MainForm.cs` отвергнут до скачивания зависимостей, сборки и подписи.

Во время проверки исправлены два воспроизводимых сбоя файлового модуля: гонка при одновременном закрытии и попадание диагностики WinFsp в протокол ответов. Добавлены однократное закрытие и отдельная метка ответов. Также повреждённый предыдущий комплект больше не сохраняется как цель отката.

Windows Hello на настоящем устройстве заново не проходил биометрическую проверку: песочница не предоставляет этот сценарий. Проверялись сохранение и обработка его ключевого материала. Работоспособность всех сайтов с ключами доступа тоже не доказана тестом двух браузеров на локальном тестовом сайте.
